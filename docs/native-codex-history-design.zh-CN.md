# Codex 原生历史与 Aether 数据边界设计

状态：**待实现设计**，不是已完成功能说明。2026-10-26 基于 `codex/aether-next` 的现有实现审查；当前使用方式见 [Codex 原生智能体](native-codex.zh-CN.md)，已验证的范围见[互通验证报告](native-codex-interop.zh-CN.md)。本文不承诺已实现 Desktop 实时同步。

## 目标与已知协议边界

Codex 是原生会话执行历史的唯一权威来源。Aether 通过原生接口读取和展示历史，保存自己的科研信息与未交付输入，不维护另一份可以独立修改的 AI 历史。现有 Aether 后端保持原有数据模型。

本机 `codex-cli 0.164.0-alpha.11.1` 导出的 schema 已确认：

| 能力                           | 已确认的静态事实                                                                                  | 设计约束                                                        |
| ------------------------------ | ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `thread/turns/list`            | 存在于稳定 schema                                                                                 | 可作为分页读取 turn 的候选接口；分页一致性仍需运行验证          |
| `thread/items/list`            | 存在于稳定 schema；必填 `threadId`，可选 `turnId`、`cursor`、`limit`、`sortDirection`，默认升序   | 使用原生分页与顺序，不从本地消息时间推断完整历史                |
| `turn/start.approvalsReviewer` | 存在于稳定 schema；枚举为 `user`、`auto_review`、`guardian_subagent`，后者为兼容旧值；默认 `user` | reviewer 覆盖本轮和后续轮，权限设置需按会话管理并验证实际生效值 |
| `thread/settings/update`       | 实验接口                                                                                          | 不把它作为稳定版本必需依赖                                      |
| Desktop IPC 实时接入           | 尚未完成实际互通验证                                                                              | 不把“共享线程存储”当作“已经共享实时事件与执行权”                |

这里的“稳定”指该安装生成 schema 时的接口分类，不表示所有 Codex 版本都支持，也不表示运行时行为已验证。开发时需按实际安装能力选择读取与更新路径，明确报告不支持的功能。

## 现有消息表为什么不能直接删除

当前 `native/session.ts` 的 `queue()` 通过本地用户消息、对应 assistant 和 `engine.cursor` 计算待发送内容。未立即要求回复的 `noReply` 科研上下文也保存在消息表；普通消息已有失败回复时，不会自动重新排队。

调用 `turn/start` 前会推进 `engine.cursor`，避免传输失败后重放可能已经执行的输入。因此现有消息表同时承担历史、待发送队列和部分发送记录，不能直接视为纯缓存。

此外还有这些依赖：

- `Session.messages()`、`MessageV2.page()` 从本地消息表读取；搜索直接查询消息与 part，导出也使用本地历史。
- 阅读引用、文件引用和对话引用中有 `ignored` 元数据，并未原样发送给 Codex，不能保证从原生历史恢复。对话引用还使用 Aether `sourceMessageID`。
- `NativeInput` 保存的上传资源可能以本地路径进入 Codex 历史；阅读模式另存 PDF、批注和阅读位置。
- 当前删除 Aether 会话会删除这些资源，但不会相应删除 Codex 原生线程。将该操作改成“解除关联”时必须同步调整资源生命周期。

主要代码入口：`packages/opencode/src/native/{session,events,input,tree}.ts`、`packages/opencode/src/session/{index,message-v2,session.sql,backup}.ts`、`packages/opencode/src/server/routes/reading-mode.ts`、`packages/app/src/components/prompt-input/submit.ts`。

## 最小持久化模型

以下是逻辑边界，不要求为每行建立独立数据库表。字段名仅表达数据含义，正式 schema 随实现确定。

| 数据                 | 必要内容                                                                                      | 权威性与清理规则                                     |
| -------------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 原生关联             | Aether session、后端、主机与原生存储身份、thread ID、迁移版本                                 | 对关联关系权威；不能仅凭项目路径合并不同存储中的线程 |
| 待发送输入（outbox） | 稳定请求 ID、会话、顺序、输入与附件引用、创建时间、状态                                       | 对未交付输入权威；不能随显示缓存删除                 |
| 发送记录（ledger）   | 请求 ID、包含的 outbox 条目、thread/turn ID、发送与确认时间、结果、不确定状态、必要的输入摘要 | 对 Aether 的交付事实权威；turn ID 在确认前可为空     |
| 科研元数据与资源     | PDF、批注、阅读位置、引用锚点、资源归属及引用关系                                             | Aether 权威；与 AI 历史分别保存                      |
| 历史缓存与搜索索引   | 原生身份、原始 item 与显示投影、原生顺序、同步范围、投影版本                                  | 可重建；不能作为继续执行或修改原生历史的唯一依据     |

outbox 与 ledger 可以由同一模块管理。绑定记录还应保存会话级设置，避免通过修改 Codex 全局配置实现单会话选项。历史缓存应能标记未完整加载、离线和失效，不把局部缓存展示成完整历史。

## 输入交付与不确定结果

1. 在调用 Codex 前持久化输入及待发送资源；检查、转换失败时保留此前未交付的 `noReply` 上下文。
2. 原子记录本次请求包含哪些 outbox 条目，并进入 `dispatching`；同一条目不能被两个请求同时消费。
3. 收到原生确认后记录 turn ID 并转为 `accepted`。执行随后失败，与“从未送达”是不同状态。
4. 发送开始后断线或超时，记录为 `uncertain`，保留输入并禁止自动重发；重连后先通过原生历史对账。
5. 只有明确未发送的输入才能安全重新排队。无法证明交付结果时，显示状态并允许用户检查原生线程，不能静默创建替代线程或重放工具操作。

当前请求已携带 `clientUserMessageId`。本机短文本验证中，它通过用户 item 的 `clientId` 返回，可用于交付对账；这并不证明重复请求会被去重或“恰好执行一次”。旧会话若没有足够信息证明某轮的结果，迁移时保留不确定状态。

## 稳定身份、未知内容与附件

历史身份使用“原生存储身份 + thread + turn + item”。显示层可以据此生成稳定 ID，但不按 ID 字符串排序；顺序由原生分页结果确定。`NativeEvents` 当前生成的本地 Part ID 不能直接作为历史对账键。

流式事件与历史读取共用同一套身份映射。子智能体的 thread/turn 身份必须保留，不能将不同子线程的同名 item 合并。新建分叉线程属于新的命名空间。旧 `sourceMessageID` 通过迁移映射转为原生引用；无法定位的引用保留快照并显示来源不可用，不猜测匹配对象。

已知 item 转换为对应显示组件；未知 item 保留可重新解析的数据并显示类型与不支持状态，不静默丢弃。显示层的截断不能被当作原生历史完整，也不能把截断缓存重新作为执行输入。

上传文件、截图和阅读 PDF 分清两类：Aether 管理的资源，以及用户工作区中的外部文件。仅清理 Aether 管理且没有有效引用的资源。解除会话关联不等于删除仍被原生线程引用的附件；没有证据证明原生端已经自持副本时，应保留资源。外部文件不存在时显示不可用，不自动替换路径或删除外部文件。

## 读取、实时事件与执行归属

先完成可重复的历史读取，再开放实时跟随。若协议支持一致的快照与事件位置，先建立订阅并缓冲事件，再读取历史并按身份合并。若没有可用的事件序号或恢复游标，不能靠“文本内容相同”消除 delta；断线后重新读取权威 item 状态，再恢复展示。

历史刷新既要补充新项，也要处理回退、压缩和其他导致旧投影失效的变化。翻页期间收到更新时，应重建受影响范围，不能假定所有变化都是向尾部追加。

读取同一线程不代表有权同时执行：

- 一个线程同一时间只允许一个经验证的执行方处理发送、取消和审批。
- Desktop 已在执行、而 Aether 尚无受支持的请求转发通道时，Aether 只读跟随，不能另起独立执行来接管。
- 一次 `thread/read` 返回 `active` 或非活跃状态都不是跨进程锁。必须验证 owner/follower 协议或其他原生互斥机制。
- 失去 owner、订阅或连接时，暂停依赖执行归属的操作；不将 Aether 的本地进程状态冒充 Desktop 状态。

## 归档、删除、搜索与导出

| 操作                     | 预期语义                                                                       |
| ------------------------ | ------------------------------------------------------------------------------ |
| 从 Aether 隐藏或解除关联 | 不改变原生历史；明确保留哪些科研信息与资源                                     |
| 原生归档/取消归档        | 使用 Codex 对应能力并刷新投影；接受其他客户端可见状态一起变化                  |
| 删除科研资源             | 单独检查归属与引用，不与显示缓存清理混用                                       |
| 删除原生线程             | 仅在原生能力明确支持且用户明确选择时提供；不能用本地删除伪装成功               |
| 搜索                     | 使用可重建的原生历史索引，并说明索引尚未覆盖的范围                             |
| 导出                     | 区分原生历史快照与 Aether 科研数据；标记读取失败或不完整，不宣称可独立恢复执行 |

现有 Aether 原生会话备份导入限制继续保留，直到有经过验证的原生恢复方案。分叉、回退、压缩等历史操作也应通过 Codex 执行，再刷新 Aether 投影，不能只修改本地消息。

## 迁移步骤与退出条件

1. **分离本地职责。** 引入 outbox/ledger 与科研元数据存储，识别旧 `engine.cursor` 之前的已派发内容和之后的待发送上下文；旧消息继续保留。无法判定的记录单独标记，不自动重放。
2. **旁路读取与对账。** 分页读取原生历史并建立稳定映射，核对用户输入、回复、工具、附件、子线程和未知 item。此时仍使用现有界面历史，记录差异，不覆盖原数据。
3. **切换读取入口。** 原生会话统一通过“Codex 历史 + 待交付输入 + 科研元数据”展示，接通分页、引用、搜索和导出。原生读取失败时显示最后一次缓存与同步状态。
4. **验证实时跟随。** 在确认 Desktop/VS Code 的连接与执行归属机制后接入事件；没有可靠通道时保留刷新读取，不宣称实时同步。
5. **允许清理旧缓存。** 仅对已完成迁移、元数据与资源已分离、可从原生历史重建的会话开放清理。原生线程缺失、数据不完整或身份无法对应时保留旧只读记录。

每一步独立可回退。回退应用版本不能重新发送已经 accepted 或 uncertain 的输入；迁移版本与发送记录必须向后兼容或阻止不兼容版本执行该会话。

## 验收矩阵

| 场景                                 | 必须验证的结果                                                  |
| ------------------------------------ | --------------------------------------------------------------- |
| Desktop 新增完整一轮，Aether 刷新    | 用户输入、回复、工具、图片按原生顺序出现；重复刷新无重复消息    |
| 多页历史与实时更新交错               | 无漏项、错序和重复 delta；未知 item 可见且不造成解析中断        |
| `noReply` 后重启或预检查失败         | 待交付上下文仍在；已失败普通消息不会隐式重试                    |
| 发送前、写入后未确认、生成中分别断线 | 状态正确区分；不确定请求不自动重放；恢复能对账                  |
| 外部客户端正在执行                   | 不产生第二个执行方；断线或 owner 不明时不能发送、取消或误答审批 |
| 原生回退、压缩、分叉、归档           | 本地投影按原生结果更新；引用不串到别的消息                      |
| 清除显示缓存后重建                   | 历史可恢复；科研批注、阅读位置、引用和资源不丢失                |
| 隐藏/解除关联与删除资源              | 语义分开；Desktop 仍使用的 Aether 管理附件不被误删              |
| 原生线程不存在或接口不支持           | 明确显示缺失/不支持；保留旧记录，不静默另建线程                 |
| Aether 原后端、搜索、导出            | 原后端行为不变；搜索和导出不把局部缓存冒充完整原生历史          |

自动化验证使用独立临时存储与确定性数据。真实客户端互通验证使用专门的测试线程，避免对既有科研对话进行回退、删除或重复执行。
