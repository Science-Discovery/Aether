# 沙箱任务书模板（任务会话用）

把 `{...}` 占位符替换后经 `prompt_async` 发给任务会话（**会话必须建在沙箱 directory**——directory 决定 bash cwd，是"任务跑在沙箱"的根本保证）。当前会话模式同样沿用本模板：把 `{WORKTREE}` 换成当前工作区即可；"完成与停止"节不适用（review 闭环在当前会话内自己执行：派 subagent → FAIL 返工循环到 PASS → PASS 后放行）。

---

你是任务执行 agent，负责 Aether 仓库（aether-dev）的第 {NUM} 号任务。你的会话直接建在沙箱工作区里，**你的 bash 默认 cwd 就是沙箱 `{WORKTREE}`**——所有 git 与文件操作都在当前沙箱内进行。

## 工作目录约定（必须遵守）

- bash cwd 即沙箱 `{WORKTREE}`（主 agent 分配，初始基于 upstream/dev）：git 与文件操作直接做，无需 `git -C`。
- **禁止改动主工作区与其他沙箱的任何文件**；不要切走别的分支。

## 任务

{任务描述}。先读参考报告 {REPORT} 确认原文与全文（含"修复执行建议"），再读对应源码确认问题在当前基线仍存在（基线 = upstream/dev）。基线红名单：{BASELINE}（整批共享，含基线 commit 号；为空时按"测试要求·基线差分"自跑）。

## 准备步骤（必做，按序）

1. `git fetch upstream dev`（如遇 ref lock 冲突，等 2 秒重试，最多 3 次）
2. `git checkout -b {BRANCH} upstream/dev`（任务书给了基线 commit 号则从该号切，保证与红名单同源）
3. 读报告相关条目 + 相关源码（都在当前沙箱下），确认问题存在；若已不存在或与描述严重不符，停止修复，最终汇报里说明原因。
4. **历史修复考古（修 bug/功能类任务必做）**：查这个 bug 之前有没有被修过——只用**本地 git 历史**：`git log --oneline upstream/dev -S"<关键标识>" -- <相关文件>`（**不访问 GitHub、不用 gh**）。找到过修复尝试 → `git show <commit>` 读该提交 diff，必须弄清**为什么 bug 仍然存在**（没修住/修好又复现/另一调用路径绕过/后续改动破坏）：对照当前代码确认补丁是否还在、覆盖窗口是否与失败场景一致；结论写进最终汇报（与历史修复的关系、本次为何能真正修住，如新增回归测试锁定场景）。没有修复历史 → 跳过。复现类 bug 优先从"上次为何没修住"找根因。
5. **全新实现（禁止复用残留）**：基于 `upstream/dev` 新分支从零实现。历史残留（上批中断的本地/远端分支、已关闭 PR、他人实现）**只可读作参考**——禁止 checkout 残留分支续写、禁止把残留提交直接充当本次交付、禁止"审一下没问题就采纳"。汇报中可引用残留实现做对照（什么思路可取、为何重做），但代码必须本会话新写并由自己的测试验证。

## 修复要求

- 优雅、健壮、最小侵入；优先按报告"修复方向"实现，若有更优方案须在最终汇报中论证理由。
- **边界条件专项检查**：实现后自查输入/状态/时序/资源在取值域边缘或极端组合下仍正确——空输入/undefined、数值 0/负数/溢出、首末元素、并发竞态时序、失败重试、资源耗尽等枚举**仅是起点**，须按功能语义自行补全；每个边界条件要么被正确处理、要么在最终汇报中说明不适用。修 bug 类重点推演触发 bug 的边界是否被补丁真正覆盖（含考古对照出的绕过路径）。
- 严格遵循仓库 AGENTS.md 代码风格：单词条命名、避免 try/catch 与 else、const 优先、Bun API、不写注释除非必要。

## 测试要求（必须全部满足）

- **验证测试（必须）**：写临时测试验证本次修改的正确性，覆盖报告中的失败场景并全部跑通；这是工作验证手段，不要求提交进仓库。
- **保护性回归测试（按需）**：是否把测试放进仓库长期保护相关功能，根据需求自行决定（易复发、历史修复过又复现、竞态时序类建议入库）；入库则与修复一起提交并在最终汇报中说明。
- **基线差分**：**"全绿" = 相对 upstream/dev 基线无新增失败**（防基线红误判、防借基线红掩盖新问题）。基线既有红名单**整批只跑一次共享**——任务书已附（或指明路径）的直接用；未提供才自跑：`git worktree add --detach <临时目录> upstream/dev` 在临时检出上跑同一套件，用完 remove，**不切走任务分支**。
- **全量跑**：改动涉及的每个 package 全量 bun test（禁只跑单个 spec 子集）+ bun typecheck，均从 package 目录跑（禁仓库根）；Solid 响应式单测用 \*.vitest.ts（bun test 下会假通过）。
- 改 package.json 必须过 `bun install --frozen-lockfile`（本地 node_modules 会掩盖未声明依赖）。
- 起后端的测试必须 `OPENCODE_DISABLE_MOBILE=1`，不碰本机常驻 server 端口。
- Playwright e2e 可以正常运行；偶发失败先对照 dev 基线判断是否环境性（vite 冷启动/资源挤兑等），是则单次有限重跑并记录，不要直接当回归修。
- **首红记账**：本会话或监视会话复跑任一次首红，都记录失败签名（spec、断言）并按 flaky 流程判定，不能重跑过就忘。
- **测的就是 commit**：最终全量验证放在最后一次 commit 之后、`git status --porcelain` 全空时跑，此后不再改文件（返工 = 新 commit 重复本流程）。
- 以上全部通过 = **本地测试全绿**；最终汇报附实际命令、通过/失败计数与基线红名单。

## 提交（必须按序执行）

1. **禁止任何 bot 行为**：不建 issue、不用 gh、不自动访问/评论/PR 到 GitHub（读写都不做）；任务源自 issue 时仅在 commit message 与汇报里文字引用编号。
2. 测试通过后以规范 commit message 提交到当前分支（任务源自 issue 时 message 文字引用编号），**commit 只含修复+决定入库的回归测试**，临时验证测试不得混入；commit 后在 `git status --porcelain` 全空的干净工作区复跑全量（被测状态 = commit 状态）= **本地测试全绿**。**不开 PR、不 push、不跟踪 CI**——交付物就是本地分支上的 commit。

## 完成与停止（重要）

1. commit+本地测试全绿齐备后发**最终汇报**（内容见"边界"），**本会话任务即告完成，停止等待**。
2. **review 由监视会话负责**（主 agent 另派的一个会话会来盯你）——你不派 review subagent、不做 self-review、不等 review。
3. 之后若收到**返工指令**（新用户消息，含 file:line 问题清单与修复建议，来自监视会话的 review）：逐条修复关键问题、补对应测试（验证测试必补；指令指出需长期保护时补入库回归测试）、在**同一分支**追加 commit、本地测试全绿、发一条返工完成汇报（列出每条问题的处置），然后继续停止等待（可能还有下一轮返工指令）。

## 边界

- 只修本任务，不要顺手修其他问题；不要修改参考报告文件本身；不要改动主工作区与其他沙箱的文件。
- {同文件相邻区域的其他并行任务提示（如有）：改动尽量局部化，汇报中注明可能冲突区域。}
- 最终汇报：任务来源（issue 编号如有，仅文字）、分支名、commit hash、改动摘要、测试命令与通过/失败计数、基线红名单、历史修复考古结论（有无过往修复尝试、bug 为何仍存在）。收到返工指令后，返工完成汇报：逐条问题处置 + 新 commit hash + 本地测试结论。
